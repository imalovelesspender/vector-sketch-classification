# 345-class LSTM directionality ablation (independent, prepared, not yet run)

Question: on all 345 QuickDraw classes, does reading the stroke sequence in both
directions help, and is any gain explained by the larger final embedding?

This is an independent controlled ablation run from Mae's PSC project directory
(`/ocean/projects/cis260329p/mcui3/`). It does not use Anson's private run
directory. All three runs, including the bidirectional reference, are trained
fresh on the same regenerated data. Anson's archived BiLSTM-256 result (75.19% valid)
is context only, not one arm of this comparison.

## What is held identical

- Code: Mae's pipeline at `5fe0e29` plus Anson's archived `run_processed.py` and
  `run_all345.py`. Every `src/` file and the adapter are SHA-256 checked
  (`historical_source_hashes.json`).
- Data: `data/processed_full` regenerated by Sihui's `data_preprocessing/preprocess.ipynb`
  (branch `data-preprocessing` @ `a2153dd`, notebook SHA-256 `af55d144…`).
  `prep_notebook.py` turns its code cells into a script. The only edit is
  `DOWNLOAD_BOTH_VERSIONS=False`, so only the 345 `.full.npz` archives (6.45 GiB) are downloaded.
  `verify_processed.py` reads every shard and checks the metadata against
  `protocol_config.json`. It also checks that the normalization scale equals the one Sihui's
  run printed and that split counts are 43,988,874 / 862,500 / 862,500. Finally, it predicts
  the selected sample IDs and records their hashes.
- Protocol: `protocol_config.json` is a byte copy of the archived BiLSTM-256 `config.json`
  (SHA-256 `b62e0699…`). The reference run must resolve to it, apart from paths,
  `output_dir` and the manifest hash. Settings are 345 classes in manifest order,
  5,000/500 per class, >250-point sketches excluded and `default_rng(42)` per split.
  Training uses seed 42, batch 128, Adam 1e-3, weight decay 0, grad clip 1.0, 10 epochs,
  last pooling and dropout 0. The best-on-validation checkpoint is kept. The test split is not touched.
- Tasks 1–2 assert that their config equals task 0's except `model.bidirectional`, `model.hidden_dim`
  and `output_dir`. They also assert that their train/valid sample IDs equal task 0's exactly.
- Hardware/software: GPU-shared, 1x V100-32, 5 CPUs, `pytorch/26.05-2.11-py3`.

## Steps on PSC

```bash
M=/ocean/projects/cis260329p/mcui3
# preprocessing checkout: $M/qd-data @ a2153dd, with prep_notebook.py, verify_processed.py,
# preprocess.sbatch and protocol_config.json in its root
cd $M/qd-data && module load pytorch/26.05-2.11-py3
python prep_notebook.py --download-only data_preprocessing/preprocess.ipynb download_full.py
SSL_CERT_FILE=/etc/pki/tls/certs/ca-bundle.crt python -u download_full.py   # login node
python prep_notebook.py data_preprocessing/preprocess.ipynb preprocess_full.py
sbatch --export=ALL,PREP_ROOT=$PWD,PROTOCOL=$PWD/protocol_config.json preprocess.sbatch
# training checkout: $M/qd-ablation @ 5fe0e29, psc_run/ = run_processed.py, run_all345.py,
# historical_source_hashes.json + this folder's .py/.sbatch/protocol_config.json
cd $M/qd-ablation
python psc_run/preflight_independent345.py --data-dir $M/qd-data/data/processed_full \
  --verification $M/qd-data/processed_full_verification.json
sbatch --export=ALL,CHECKOUT=$PWD,DATA_DIR=$M/qd-data/data/processed_full psc_run/independent345.sbatch
```

The module's Python has no CA bundle of its own, so the download needs `SSL_CERT_FILE`.

## Caveats

- Single seed and a fixed 10-epoch budget. cuDNN is not deterministic, so reruns can differ slightly.
- UniLSTM-512 has more parameters than BiLSTM-256x2 (1.24M vs 0.71M).
- Compare on validation only. `evaluate_test_direction.sbatch` is optional and is a separate decision.
- The regenerated manifest may differ in bytes from Anson's (`f5810fec…`) because
  per-category statistics are recorded in thread-completion order. That is why this ablation
  trains its own BiLSTM reference.
